# 2M辞書互換性の検証（2026-09-13）

## 結論

本家の対応済みjdict.c/hで、手元の2M辞書をそのまま解析できることをホストで確認した。
ESP-IDF版に同梱された旧ローダーは辞書を開けてもmatrixc/charrを認識せず、接続コストと文字種情報を使えていなかった。
この調査では製品ソース・PlatformIO設定を変更していない。実機・読み・アクセント・音声の正しさは未検証。

## 実施した検証

既存のWSL Ubuntu / gccで旧・上流ローダーを別々の共有ライブラリとしてコンパイルし、Python ctypesから同一辞書を渡した。作業領域は既存案と同じ48 KiB、最大96形態素。

| 項目 | 旧ローダー | 上流ローダー |
|---|---|---|
| jdict_open | 成功 | 成功 |
| 接続行列サイズ | 0 × 0 | 1377 × 1377 |
| 文字種の符号位置数 | 0 | 65,535 |
| 今日は良い天気ですね。 | 7形態素 | 7形態素 |
| こんにちは。 | 2形態素 | 2形態素 |
| 東京都に行きます。 | 東／京都／に／行き／ます／。 | 東京／都／に／行き／ます／。 |
| 123個あります。 | 解析エラー -1 | 123／個／あり／ます／。（123は未知語） |
| スーパーでパンを買います。 | 7形態素 | 7形態素 |
| OpenAIで開発します。 | 解析エラー -1 | OpenAI／で／開発／し／ます／。（OpenAIは未知語） |
| ぬるぽぴょんテストです。 | 解析エラー -1 | 6形態素、未知語ぽぴょんを含む |

未知語として解析できることは、正しい読みを生成できることを意味しない。

上流ソースで定義された形式をPythonでも復号し、C APIと全件比較した。

- matrixc: 行・列を256クラスタずつへ写像し、代表行列の8bit値を整数式で復号。全1,896,129接続コストが一致（非ゼロ1,895,073件）。
- charr: 開始符号位置と値表の添字を持つ範囲表。全65,535符号位置が一致。
- 上流jdict.cを既存xtensa-esp32s3-elf-gccで `-std=c99 -O2 -Wall -Wextra` により単体コンパイル: 成功。

比較スクリプト・取得ソース・共有ライブラリは実行時の `%TEMP%/sanotts-dict-review/` に置いた。恒久的な自動テストとして組み込んだものではない。

## 移植方針への反映

1. jdict.c/hを同一コミットから対で採用する。圧縮形式だけでなく、それに関連する構造体・検査・未知語の分岐も整合させる。
2. 既存推論コアやexample01〜04は更新しない。新ローダーの追加機能rec5等も含まれるため、無関係な推論更新とは分けて扱う。
3. 辞書は圧縮されたままflashに配置する。matrixcは必要な接続コストだけ復号し、charrは範囲表を二分探索するので、巨大なRAM展開は不要。
4. 新exampleで辞書の形式・寸法・文字種情報をログ確認してから日本語解析とストリーミングへ接続する。
5. 次の確認対象はNJD・ラベル・ids変換との結合、ファームのビルド、実機メモリ、数字や未知語を含む文章の読み。
